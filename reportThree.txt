3. WHAT HAS BEEN COMPLETED

Application implementation

The application provides a learner-focused vocabulary quiz product built around
strict and casual quizzes. Guests can browse and play listed published quizzes.
Google-authenticated users can use Creator Studio to create, edit, publish,
unpublish, duplicate, and inspect quizzes.

Google authentication
- Google OAuth is implemented through Laravel Socialite.
- The callback creates or refreshes a user account from Google identity data.
- Public payloads do not expose private email addresses.
- Guest users receive persistent guest ownership tokens for run ownership.
- Socialite behavior is covered by test doubles in the feature suite.
- Live sign-in with actual Google client credentials has not yet been performed.

Quiz lifecycle
- Draft, published, and unpublished states are implemented.
- Draft saves permit incomplete quiz and question data.
- Publishing applies the complete PRD validation rules.
- Published quizzes remain immutable.
- Only drafts can be deleted.
- Published or unpublished quizzes can be duplicated as a new draft.
- Listed quizzes appear on Explore.
- Unlisted quizzes remain accessible through their share link.
- Unpublishing makes the quiz unavailable to other players and closes active
  runs on their next request.
- Draft and unpublished quiz test play is available to the creator.
- Creator test runs are excluded from counted quiz totals.

Strict mode
- The server shuffles the question order and option permutations.
- Only the current strict question is returned to the client.
- Server timestamps decide timing outcomes within the configured grace period.
- Wrong answers, timeout, and focus loss end the run suddenly.
- Strict answer indexes are validated and mapped back to original option indexes.
- Duplicate and unauthorized submissions are rejected or handled safely.
- The client pauses timer display while an answer request is being checked.

Casual mode
- The server creates a random salt and answer hashes for the client.
- The client shuffles questions and options and performs answer checks locally.
- The submitted answer log is rechecked on the server.
- Tampered answers, malformed logs, missing questions, duplicate question IDs,
  invalid option indexes, and invalid reasons are rejected.
- Creator analytics label casual quizzes and results as self-reported.

Discovery and player features
- Explore supports title and description search.
- Explore supports All, Strict, and Casual mode filtering.
- Explore supports Popular, Most played, and Newest sorting.
- Cards show quiz metadata, creator, mode, timer, question count, votes, and
  plays.
- A global top-bar search routes to Explore using Wayfinder.
- My Plays shows signed-in users' recent attempts and first-pass information.
- Unavailable published-to-unpublished quizzes are identified in play history.

Voting and analytics
- Voting is restricted to signed-in users.
- Published, listed quizzes only accept public votes.
- Creators cannot vote on their own quizzes.
- The vote row and cached upvote count are updated in a transaction.
- Run, pass, and reached totals are counted according to the creator exclusion
  rule.
- Logged-in quiz-user attempt and pass statistics are maintained.
- Creator analytics include totals, question correctness, selected wrong
  options, average answer time, failure reasons, and player summaries.
- Guests are grouped under a single Guests analytics row.

Suggestions
- Suggestions are generated from published, listed quizzes.
- The current quiz and passed quizzes are excluded for signed-in users.
- The author, pass-rate similarity, and vote weights are applied.
- Quizzes with fewer than ten counted runs use a neutral statistics term.
- Results are limited to twelve quizzes.
- Each creator is limited to three suggestions.
- The calculation is portable between SQLite and PostgreSQL.

Database and migration work
- All application migrations exist for users, quizzes, questions, votes, runs,
  answers, and per-user quiz statistics.
- The original quiz-runs create-table migration was restored to its historical
  form.
- A separate forward migration updates the user foreign key to cascade on user
  deletion.
- The same forward migration adds a PostgreSQL exactly-one-owner check:
  either user_id or guest_token must be set, but not both.
- The migration was checked for rollback and re-application.
- Existing valid run data was preserved during the PostgreSQL upgrade simulation.
- PostgreSQL rejection of ownerless and dual-owner runs was verified.
- Cascade deletion of user-owned runs was verified.
- An audit query for legacy invalid run owners is documented for use on a real
  database before migration.

Docker and environment work
- The development Compose stack has separate db, app, and webserver services.
- PostgreSQL 16 is used for Docker development.
- The app image includes PHP-FPM, Composer, Node, npm, and Vite support.
- The development image includes Composer development dependencies, so
  php artisan test and Pest work inside the container.
- The production image uses composer install --no-dev and
  --optimize-autoloader.
- The production image excludes tests and node_modules after asset building.
- Storage and bootstrap cache directories are created at image build and
  container entry.
- Runtime Laravel directories are owned and writable by www-data with 775
  permissions. The setup does not use chmod 777.
- Named Docker volumes isolate storage and cache state from the host bind
  mount.
- Host build context rules exclude .env, .env.*, vendor, node_modules,
  public/build, Laravel runtime cache directories, and generated PHP cache files.
- Git ignore rules exclude generated bootstrap/cache/*.php files and both
  secret environment file patterns.
- The tracked .env.example now uses Docker database settings, port 8080,
  file sessions, and matching Google callback configuration.
- A tracked .env.production.example placeholder file is present.
- Production Compose and deployment documentation use the same
  .env.production file name.

Documentation
- docker.md gives exact local Docker setup and Snap Docker socket instructions.
- README.md links to the Docker and production setup.
- docs/DEPLOYMENT.md documents production Compose, HTTPS, backups, and updates.
- docs/POSTGRES_SMOKE_TEST.md documents PostgreSQL migration verification.

4. DOCKER BUG FIXES JUST COMPLETED

HTTP 500 and tempnam problem

The previously reported BladeCompiler/tempnam failure was caused by an
application runtime directory being unavailable or not writable to the PHP
process in the bind-mounted container environment.

Fixes now present:
- The app Dockerfile creates storage/framework/cache/data,
  storage/framework/sessions, storage/framework/views, storage/logs, and
  bootstrap/cache.
- The production Dockerfile creates the same directories before Wayfinder and
  Vite Artisan build steps run.
- The entrypoint recreates those directories each time a container starts.
- The directories are assigned to www-data and use user/group write permissions.
- The bind-mounted host project no longer needs manual chmod or sudo changes.
- The dev Compose stack uses named volumes for storage and bootstrap/cache.

Boost stale-provider problem

Laravel Boost is only declared in require-dev. It is not referenced by
bootstrap/providers.php or application runtime configuration.

The Docker setup now:
- Installs dev dependencies in the development app image.
- Installs only production dependencies in the production image.
- Excludes bootstrap/cache/*.php from Docker build contexts.
- Ignores generated package.php and services.php cache files in Git.
- Installs production dependencies with --no-dev and
  --optimize-autoloader.

Port and redirect consistency

The development port is consistently 8080:
- docker-compose.yml maps the webserver to 8080.
- .env.example uses APP_URL=http://localhost:8080.
- Google redirect configuration uses
  http://localhost:8080/auth/google/callback.
- README.md and docker.md use the same origin and callback.
- The exact Google Cloud Console redirect URI is:
  http://localhost:8080/auth/google/callback

Database setup

.env.example now contains Docker-safe defaults matching the db service:
- DB_CONNECTION=pgsql
- DB_HOST=db
- DB_PORT=5432
- DB_DATABASE=quizapp
- DB_USERNAME=quizapp
- DB_PASSWORD=quizapp

It no longer contains a host PostgreSQL socket path or placeholder credentials.
SESSION_DRIVER is set to file.

Seeder setup

The demo seeder creates five published and listed quizzes. The verified seed
set contains:
- Three casual quizzes.
- Two strict quizzes.
- At least six questions in every strict/casual seeded quiz counted in the
  verification query.
- Demo quiz titles including Advanced English Vocabulary, Scientific
  Terminology, French Vocabulary Basics, Medical Terminology, and Business
  English Vocabulary.

8. EXACT LOCAL SETUP RESULT

On a clean clone, the documented setup is:

  cp .env.example .env
  # Add Google credentials to .env.
  docker compose up -d --build
  docker compose exec app php artisan key:generate
  docker compose exec app php artisan migrate --seed

The application is then available at:

  http://localhost:8080

Useful verification commands are:

  docker compose ps
  docker compose exec app php artisan migrate:status
  docker compose exec app php artisan tinker
  docker compose exec app php artisan test --compact
  docker compose logs --tail=100 app webserver db

To completely reset the local database and named volumes:

  docker compose down -v
  docker compose up -d --build
  docker compose exec app php artisan key:generate
  docker compose exec app php artisan migrate --seed

docker compose down -v removes local database and app cache data. It must not
be used on a production system.
